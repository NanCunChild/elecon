## 是否需要增加能力

| 目标 | 当前能力是否足够 | 需要增加或核实的内容 |
|---|---|---|
| 本轮 11 个只读业务能力及官方页登录 | SDK 2 的凭据、HTTP、DOM、Cookie 和真实 QuickJS timer 足够 | 无新增宿主 API/权限、无新业务 id；需真实学校/设备校准 |
| 卡片只返回余额但无真实卡号 | 网络/脚本足够 | 现 `card.balance` / `card.transactions` 输出强制 cardNumber；本轮允许用户明确提供，不造值。若要免配置完整兼容，应另开 ADR 调整输出契约的必填性与版本 |
| 未排课程、考试结束时刻、成绩构成 | 请求与解析足够 | 现标准输出没有对应结构；需业务契约扩展/专门能力，不能假装已有字段可无损承载 |
| 历史学期 | 不缺宿主 API | 参考只证实当前学期接口；需补实际来源，不靠推算制造历史列表 |
| 图书搜索/详情/续借 | HTTP 足够 | 需 `library.search` / 详情结构及续借写操作能力与用户交互；本轮不借只读能力触发续借 |
| 水电加密查询 | 普通 JS 可以随包包含 AES、签名与 OAuth 编排 | 需实际校园网、表具选择和字段契约；余量 `LastNum` 不能冒充累计 `reading`。多表每请求签名会消耗预算，应按表/时间窗口拆调用 |
| 体育、实验、超星学习进度、校园网余额 | HTTP/普通 JS 能处理已见协议 | 现有 schema 只覆盖部分统计，需按领域补结构；不把体育成绩硬塞学业成绩或把校园网余额当流量 |
| 空调指令、付款码、宿舍水操作 | 请求不缺 GET/POST | 需要相应业务模型、实际设备/身份选择及产品确认流程；本轮未迁入任何设备控制或付款行为 |
| 无人干预的纯 HTTP 密码/MFA 登录 | 可以实现协议，不宜把校本流程搬回核心 | 现无脚本输入 OTP/确认的通用交互 API；当前以官方可见页面完成，不需要专用 CAS/滑块 SDK |
| 长于两分钟的认证、可信设备延续 | 当前存在实际宿主边界 | 登录脚本约 100 秒、总预算 120 秒；参考企业微信重发冷却可达 120 秒。可选改进为认证续接/稳定导航等待/错误码，以及有确切需求的页面初始化存储恢复，均应先有 ADR |

SDK 2 使用的是已授权当前学校凭据；不是为每个新系统再增加权限语言。增加 `ctx.crypto` 不是这些只读能力的前置条件。平台未提供完整 Cookie 元数据、WebView 每次清理 storage、校外网络不可达等事实仍存在；不能把可见页面登录描述为参考仓完整浏览器身份/指纹持久化的等价替代。

本轮确实需要一项 SDK 实现修复：锁定的 QuickJS 绑定漏处理长拼接字符串的 `STRING_ROPE` 标签，导致正常课表被误报 `output_limit`，也可能损坏长凭据/请求/页面源码。已在现有字符串跨桥前线性化并通过真实 QuickJS 回归；这没有新增 API、权限或放宽输出校验。仅 Node 模拟测试无法发现该绑定差异。
