# 脚本执行原语与数据刷新讨论

日期：2026-11-05。状态：**讨论共识与候选设计，接口尚未定稿或实施**。承接 [ADR-080](../adr/adr_080_trusted_script_extensibility.md) 与 [ADR-081](../adr/adr_081_script_runtime_consolidation.md)；现行边界以[当前架构](../architecture.md)为准，实施状态只在[统一计划](../planning/implementation.md#受信扩展)维护。

核心提供执行作用域、处理器注册、调度、消息通信和业务过程记录等通用设施；学校脚本组合这些设施实现刷新、监控和业务操作。核心不需要理解学校协议，但必须知道执行所属身份和来源、触发依据、资源预算及停止条件。后续[ADR-097](../adr/adr_097_registered_script_execution.md)已将前台注册执行定稿为 SDK19；其余候选机制不能据此视为已实施。

## 事务指可跟踪的业务过程

本讨论中的“事务”指一次具有运行标识、触发来源、参数、阶段和结果的业务过程。它可以由按钮、已启用的计划或有效会话中的事件发起，经历排队、运行、等待交互、成功、失败、取消、错过或结果未知；具体状态及转换仍需契约化。

一个业务过程可以包含多次短调用和等待，不要求始终占有一个 QuickJS 实例。学校脚本负责学校业务的步骤与成功判定，核心负责过程关联、生命周期和可解释的运行记录。记录不包含密码、验证码或未经约束的私密响应正文。

此处不赋予数据库原子事务含义，也不承诺远端操作可回滚。取消不能撤回已经送达学校的提交；发送后失去结果证据时保留未知，不因本地缺少成功记录自动重发。

## 广播需要实际的事件来源和存活设施

广播或发布订阅负责分发已经产生的事件。要通知或唤醒另一方，必须有仍在运行的生产者、计时器、消息代理，或平台支持的外部唤醒设施承接事件。注册监听器本身不能发现学校网站变化，进程内事件总线也不能自行唤醒已退出的应用。

不要求某一个 JS 实例永远存活：宿主仍在运行时，可以由宿主计时器触发新的短调用；应用进程退出后，则需要独立于该进程的系统调度或其他已实现的外部入口。届时必须说明实际平台条件和错过策略，不能把普通 JS 定时器或本地广播描述成持久唤醒能力。

区分两段通信：学校服务向脚本提供变化，脚本向核心界面发布结果。前一段没有推送接口时仍需轮询；后一段可以使用发布订阅，减少界面与取数流程的耦合。DOM 观察只发现已加载页面实际发生的变化，也不能替代源站取数。

## 课表使用轮询和新鲜度策略

本讨论的课表场景没有服务器主动通知客户端的机制。因此不以“收到课表变化广播”作为发现更新的起点，而采用以下流程：

```text
页面访问、恢复前台或可用的定时触发
  → 检查当前身份、来源和查询参数对应的数据新鲜度
  → 尚新鲜：继续使用已有快照
  → 需要刷新：调用学校脚本拉取课表
  → 成功且结果仍有效：替换对应快照，记录实际取得时间
  → 通知订阅界面读取新快照
```

这里的定时触发可以只是周期性检查新鲜度，不意味着每次检查都请求学校。刷新间隔和建议时机由学校策略提供，宿主负责通用调度、调用去重和生命周期；具体配置归属与接口留待设计。

数据年龄超过阈值表示需要重新检查，不证明源站已经变化。普通刷新取得有效完整结果后可直接替换对应快照，不要求先做差异检测。如果产品需要提示“课程发生变化”，则应在取得新数据后进行有明确实体语义的比较。

刷新失败保留可展示的旧快照及其原始取得时间，并表达过期或失败；不能因检查时间到了就把旧数据标为新鲜。成功取得相同内容可以更新实际取数时间，但不能因此声称课程发生变化。源站更新时间若未知就保持缺失，不用本地取数时间冒充。

广播发生在拉取和更新之后，用来通知消费者。若没有存活的计时设施或可用的外部唤醒条件，期间不会主动更新；下次页面访问或执行恢复时再检查新鲜度。是否允许后台轮询须由对应生命周期和平台能力明确支持。

## 可复用原语的职责

| 原语 | 核心职责 | 脚本职责 |
|---|---|---|
| 执行作用域 | 绑定 Profile、学校、批准来源、取消与资源；回收所属执行、计时器和订阅 | 在当前作用域内组合学校业务 |
| 处理器注册 | 将稳定名称解析为批准包中的确定入口；运行前复核授权 | 只注册需要宿主再次进入的函数，内部逻辑保持普通 JS |
| 调度注册 | 按时投递、取消或替换登记，管理重复与错过 | 指定目标处理器、业务状态的存储引用和所需时机 |
| 发布订阅 | 来源绑定、作用域、投递与流量管理 | 发布已经取得的内容或已经观察到的事件 |
| 业务过程记录 | 关联一次运行的触发、阶段、取消和结果 | 判定业务成功、失败及可恢复阶段 |

页面临时刷新属于页面作用域，页面关闭应撤销尚未开始的工作并拒绝迟到发布。用户已启用的持久计划属于计划作用域，关闭设置页面不等于取消计划。安装脚本或展示入口不自动启用持久自动操作。

所有交给核心注册并再次执行的处理器均不得携带注册现场的临时上下文，包括仅在当前会话内使用的注册。注册引用批准包中的稳定入口名，核心不接收函数对象或捕获闭包；处理器需要跨执行取得的业务参数、配置和中间结果必须先写入相应存储库，执行时通过存储引用读取，不以注册参数快照变相携带临时业务状态。旧调用的 ctx、连接、页面对象和可变模块变量也不能成为后续执行的隐式依赖。

每次执行的身份、取消信号、运行标识等宿主上下文由核心重新构造。批准源码中的常量和普通辅助函数可以复用；本约束针对宿主注册入口的跨执行状态传递，不禁止一次执行内部使用普通 JS 局部变量和闭包。注册与装载机制须落实这一边界，具体工具链检查和运行时隔离方式仍待接口设计，不能仅靠函数名称声称已经阻止上下文捕获。

存储库按状态寿命区分：页面临时业务状态可以使用随作用域销毁的内存存储，跨进程恢复需要持久存储；凭据和挑战材料沿用受保护且有期限的存储边界。要求从存储读取不意味着所有数据都写入磁盘，也不使二维码图片进入普通持久缓存。需要恢复的注册保存稳定入口、存储引用、身份及批准 digest 等绑定；包更新不能让旧计划默默改用新代码。状态缺失、过期或不再属于当前身份时应给出明确结果，不回退使用残留内存。

刷新策略与引擎复用分别设计：脚本申报下次调用时刻，并不要求保留 JS 实例；脚本持续监听并发布则需要独立的长期会话。订阅等待不能一直占住所有普通调用共用的串行队列；并发调整仍须协调共享凭据和存储。

## 消息含义与待定契约

本轮决定沿用现有缓存与 `homeDataRevision` 通知，卡片摘要与二级页先不新增通用广播。多消费者共享状态优先采用存储快照及键/版本通知：生产者更新存储，消费者收到变化后读取；新页面直接读取当前快照。订阅与初读必须避免竞态漏更新。二维码使用所属作用域的定向结果，按钮命令不广播。只有必须保留每条事件时再设计历史、顺序与确认。

二维码或当前状态可以采用保留最新快照的输出通道；需要历史的事件须另定保存、顺序、重复和确认规则。广播通知没有隐含的执行授权。“提交选课”等有副作用的请求应指向确定处理者，并关联业务运行，不能因多个订阅者或事件重放产生重复提交。

核心可以不理解学校业务语义，但原生展示仍消费标准契约，消息仍须绑定真实来源和授权身份。同校通道的命名空间用于寻址，不能被描述为包间独立的最小权限沙箱。

后续定稿需要明确注册的生命周期与幂等性、时间和错过规则、快照与事件的区别、投递保证、重启恢复、运行状态及版本迁移。接口落地前按已有 ADR 覆盖范围实施；新增架构或契约决定先形成 ADR，不把本讨论中的候选原语直接写入生产包。
