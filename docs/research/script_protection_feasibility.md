# 学校脚本混淆、加密与 QuickJS 虚拟化保护研究

日期：2026-11-01。范围：本轮所有者要求的可行性研究；未改引擎、未加入保护依赖、未新增加密包格式。当前 `elecon-script/1` 仍是可检查源码与 digest 授权，不能把研究直接当作生产接口。

## 结论

**可以 fork flutter_qjs_next 内嵌的 QuickJS，改 opcode、解释器或引入私有虚拟指令；不建议首片就维护整套 VMP 引擎。** 优先在构建阶段对少数纯计算函数做可选保护；先保留可检查的认证、网络与 SDK 调用。若要分发不含可检查源码的加密/字节码包，需要另立 ADR、版本与授权模型，不能复用源码安装界面并声称用户已检查实际执行内容。

混淆、打包加密和虚拟化解决不同问题，均不能把交付到用户设备的算法、解密密钥或运行时凭据变成不可提取的秘密。以下收益/成本判断属于本地代码审计与公开技术资料基础上的工程推断，没有测得运行开销或抗逆向时间。

## 本地事实与可修改位置

当前两个生产 pubspec 均精确固定 `flutter_qjs_next: 1.2.1`。核对 pub 缓存中该版本的 LICENSE、README、Dart FFI 和 C/C++ 源码；不以远端主分支替代已解析依赖：

| 位置（相对插件根目录） | 已观察到的事实 | 对方案的影响 |
|---|---|---|
| `cxx/quickjs/quickjs.c` 的 `JS_CallInternal` / `SWITCH(pc)` | 原生字节码解释循环，包括 computed-goto/switch 两条派发路径 | 可修改解释器，但两条派发、编译与指令描述必须一致 |
| `cxx/quickjs/quickjs-opcode.h` | opcode 与指令尺寸/栈效果定义 | 随意重排可能破坏短指令、连续指令及编译器假设；不能仅随机改枚举 |
| `cxx/ffi.cpp:695` 附近 `CompileScript` | `JS_Eval(COMPILE_ONLY)` 再 `JS_WriteObject` | 已有编译入口，但当前包装的脚本编译不等于完成宿主 ESM 模块加载改造 |
| `cxx/ffi.cpp:712` 附近 `EvaluateBytecode` | `JS_ReadObject` 再 `JS_EvalFunction` | 已有二进制载入路径，不代表任意下载字节码安全可用 |
| `lib/quickjs/ffi.dart` | 存在 evaluateBytecode 绑定 | 仍须扩充背景 isolate、模块解析、产物版本与授权链路 |
| `cxx/ffi.cpp` interrupt 装配 | 已有执行中断钩子 | 新解释循环必须维持超时/取消，不得把保护层变为预算逃逸点 |
| README / native 构建目录 | 声明内嵌 QuickJS 2026-06-04；源码用于原生构建 | fork 应固定提交并同步各平台原生副本，禁止改 `.pub-cache` 作为交付 |

插件和 QuickJS 的 MIT 许可允许修改与分发，需保留版权/许可；另引入保护器时仍需独立检查其许可。来源：[插件上游](https://github.com/NanCunChild/flutter_qjs_next)、[QuickJS 官方手册](https://bellard.org/quickjs/quickjs.html)。此处没有安装或升级到插件最新版本。

## 选项比较

| 方案 | 能达到什么 | 主要代价/限制 | 当前适配 |
|---|---|---|---|
| 构建期压缩、局部变量重命名 | 去注释、降低可读性，通常减少体积 | 很容易被格式化，保留字符串与主要控制流 | 当前 esbuild 工具已存在；应由作者选择，最终源码 digest 授权 |
| AST 混淆、字符串编码、控制流改写 | 提高静态阅读/批量抄取成本 | 调试困难，体积和 CPU 成本须实测；不能改 SDK 属性或 ESM 导出语义 | 可在打包前处理纯函数；例如 [javascript-obfuscator 官方项目](https://github.com/javascript-obfuscator/javascript-obfuscator) 提供这些选项，尚未引入 |
| AES-GCM 加密包/源码 | 隐藏静态分发内容，对没有密钥的存储副本提供保密性并验证完整性 | 客户端须能解密；攻击者可抓明文、密钥或解密后的数据。安装检查与执行字节对应关系须重设计 | 不应在现有源码包中暗加透明解密 |
| 标准 QuickJS 字节码与剥离调试信息 | 少暴露原始文本，减少部分解析工作 | 可以反汇编；格式与引擎版本绑定，二进制解析扩大攻击面 | 官方明确警告字节码执行前不做完整安全检查，不加载不可信来源；digest/用户点击不等于字节码内存安全 |
| 定制 QuickJS opcode 映射/序列化、分块编码 | 使通用反汇编工具失效，抬高初始分析成本 | 解释器和密钥仍在客户端，动态转储可恢复；每次引擎升级都要维护编译器/解释器/读写器一致性 | 技术可行，尚无证据值得承担全平台维护成本 |
| 对少数函数做自定义 VM（接近 VMP） | 将选定算法翻译成私有指令与解释器，保留学校 JS 外壳 | VM 也能被分析；需处理类型、异常、闭包和调试，代价与性能未知 | 更适合先限定同步、无 I/O 的纯计算函数；可先用 JS VM 做实验，不开放任意原生模块 |

QuickJS 的字节码版本限制与信任警告见[官方 Script evaluation](https://bellard.org/quickjs/quickjs.html#Script-evaluation)。加密层不能替代网络范围、Profile/学校身份、安装 digest 或命令确认。运行中的登录协议必须实际发出学校能识别的请求，保护层也不能隐藏对设备所有者可观测的行为。

## 若继续试验，推荐的最小切片

1. 选一个合成、无 I/O 的纯计算函数，保留原实现与固定输入输出向量。作者侧通过显式构建选项选择压缩或局部 AST 混淆；固定随机种子/工具版本，保留私有调试映射，不把 sourcemap 和密钥一起公开分发。
2. 保留 `capabilities` ESM 导出、SDK 属性名、学校网络声明及版本语义；避免 `selfDefending`、`debugProtection`、domainLock 和浏览器全局假设。先在真实 `IsolateQjs` 验证闭包、Promise、HTML stdlib、异常、取消、输出、日志遮蔽及凭据访问，再验证真实学校模块的合成夹具。
3. 测量同一设备/构建下未保护与保护版本的冷启动、CPU、峰值内存、包大小和超时率，写明数据集与重复次数。没有测量前不声称“几乎无开销”或“VMP 级保护”。
4. 确有收益再研究局部 VM。仅翻译受限纯函数；网络、凭据和 UI 仍通过原宿主接口。禁止保护插件动态侧载原生模块、FFI、文件或进程。
5. 只有源码保护仍不满足需求才单独提出二进制格式：新容器版本、引擎/VM ABI、认证加密封装、产物来源校验、回滚/吊销、平台构建重现、畸形输入 fuzz 与测试矩阵。编译器与加载器成套固定；不能把通用未验证 QuickJS 字节码直接作为学校包载入。

本轮只完成研究。没有修改 QuickJS、加入加密加载器、提供可调用的 VMP 开关，亦无平台性能或人工安全签收证据。
