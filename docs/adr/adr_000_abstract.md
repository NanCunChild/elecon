# ADR-000：总体架构路线（Abstract）

- **状态**：已接受（Accepted）
- **日期**：2026-06-07
- **适用范围**：整个项目的顶层技术路线。本文是"总纲"，后续按 `adr_001`、`adr_002` … 拆分单点决策，凡与本文冲突者以更晚的、显式声明覆盖本文的 ADR 为准。
- **项目代号**：Elecron

---

## 1. 背景与问题（Context）

存在一个学生自用的校园信息聚合应用，当前面临结构性困境：

1. **维护人力不足**：维护者精力有限，难以持续追逐变化。
2. **学校接口频繁变动**：教务、一卡通、图书馆等后端接口随时改，每次都要发版跟进。
3. **开源社区助力不足**：贡献门槛高，外部贡献者难以参与。
4. **合规风险**：私密的学生数据如何处理、存在哪里，缺乏清晰的边界。
5. **既有技术债**：已有一个可用的 Flutter 应用，但与学校接口深度耦合，且背着旧债。
6. **形态割裂**：iOS / Android / HarmonyOS 三分天下；校内可直连，校外受网络与微信绑定限制。

核心矛盾是：**变化频率高，而能投入的维护资源低。** 因此架构的第一目标不是功能最大化，而是"在最少的人力下，让系统对学校侧的变动与平台侧的差异保持韧性"。

---

## 2. 决策：总路线（Decision）

采用 **shim + 中转 + 本地优先（local-first）** 的分层架构。一句话路线：

> **把"会变的内容"沉成可热替换的运行时配置，把"必须可信的东西"收敛进一个不可绕过的核心；公网组件保持"哑"和无状态，私密数据永不离开客户端或校内授权环境。**

### 2.1 一条贯穿全局的主线

**让公网服务端尽量"哑"和无状态。** 它只做两件事：分发 adapter / UI 描述、缓存公开（非私密）数据。私密、认证相关的数据永远走客户端直连或校内堡垒机。这一条同时解决三件最难的事：

- **成本**：哑组件可退化为静态托管 + 极小的无状态服务，长期开销趋近于零，不依赖捐赠续命。
- **合规**：私密数据不经公网服务器，合规面大幅收窄。
- **安全**：公网服务器不持有任何可重放凭证，被攻破也不会泄露学生身份。

### 2.2 分层结构

```
┌──────────────────────────────────────────────────────────┐
│  UI 层（表现）                                              │
│  数据驱动 / Server-Driven UI，消费"标准 schema"渲染卡片     │
├──────────────────────────────────────────────────────────┤
│  可信核心（Core / Broker）—— 不可绕过、不可被插件替换        │
│  · 凭证保管：cookie/token 只存于此，不出核心                 │
│  · Capability Broker：按白名单注入凭证、限定 adapter 能做什么│
│  · 插件运行时与信任策略：签名校验、吊销、dev 侧载闸门         │
│  · 版本/时效解析：代码用版本号，数据用 TTL/新鲜度            │
├───────────────────────────┬──────────────────────────────┤
│  数据 adapter 层（逻辑）   │  传输底座层（Transport）         │
│  · QuickJS 脚本，可热替换   │  · 原生模块，仅官方签名可加载     │
│  · 把"某校接口"→"标准schema"│  · direct / 系统VPN / app内隧道  │
│  · 按信任级分能力档         │  · 可替换但不是脚本插件          │
└───────────────────────────┴──────────────────────────────┘
        │                                  │
        ▼                                  ▼
┌────────────────────┐          ┌──────────────────────────┐
│ 校内授权中继(campus)│          │ 公网哑服务(public)         │
│ 堡垒机后、信息处授权 │          │ 无状态：发 adapter + 缓存   │
│ 代取私密数据         │          │ 公开数据，不持有任何凭证     │
└────────────────────┘          └──────────────────────────┘
```

### 2.3 关键契约（整个项目最重要的设计产物）

- **标准数据 schema**：adapter 与 UI 之间唯一的耦合面。adapter 负责"某校特有格式 → 标准 schema"的归一化；UI 只认标准 schema，与学校无关。
- **Capability Manifest**：adapter 声明"我能提供什么数据 / 我需要访问哪些域名"；UI 声明"我渲染什么卡片"；核心据此撮合，并据 manifest 的域名白名单做凭证注入。

### 2.4 版本与时效（易踩坑，单列）

- **代码（adapter / UI 描述）用版本号**：取 `max(本地版本, 服务端版本)`，谁新用谁。这正是应对"学校接口频繁变动"的机制——推一个新 adapter 版本即可，无需走应用商店发版。
- **数据用时效 / TTL**：私密数据本地直连最新鲜；公网缓存只在校外或学校侧故障时兜底。**不要用版本号去判数据新鲜度。**

## 3. adapter 与 QuickJS 的关系与作用（核心，单列）

这是整个路线的承重墙，必须讲清。

### 3.1 adapter 是什么

adapter 是**逻辑**，不是数据，也不是底座。它的唯一职责是把"某个学校后端返回的混乱数据"归一化成"标准 schema"——但**这份职责本身是重活**：脏格式清洗、校本特有派生（如从校历推当前教学周）、多接口拼装、跨校差异抹平，全部压在这一层。它是系统中**变化最频繁、最该被隔离**的部分，因此被设计成：

- **运行时可热替换的脚本**，而不是编译进 App 的代码；
- **能力面越薄越好，功能面越重越好**（见下「两个轴」）。

**「越薄越好」是安全口号，不是工程口号（2026-07-23 澄清）。** 这句口号约束的是 adapter 的**能力 / 信任面**，不是它的**代码量 / 功能复杂度**——两者是正交的两个轴，长期被这一句话混为一谈，造成"adapter 少干活才是对的"这一误读。澄清如下：

- **能力面（安全轴，越薄越好，红线 #5）**：不可信 adapter 无凭证、无网络、无副作用、不驱动渲染、不做跨数据源编排。这是承重墙，不可退让——`release` 下侧载 adapter 恒为 declarative 纯解析。
- **功能面（工程轴，越重越好）**：adapter 是**吸收对端混乱的 shim**，是整个系统里功能复杂度**最应该集中**的地方。归一化越彻底、把越多校异脏活关进这个**可热替换、可隔离、可夹具回归**的盒子，上层（UI / 本体 / 核心）就越干净、系统对学校接口变动越有韧性（呼应本文第一目标）。**工程上我们期望 adapter 尽量重，而不是尽量薄。**

分工线由此清晰：**对端原始事实的归一化 + 校本特有派生 → adapter（尽量重）；跨校统一、本体要施加智能的派生语义（算 GPA、排序、聚合、提醒）→ 本体；凭证 / 网络 / 渲染 / 跨源编排 → 核心（能力面，adapter 永不碰）。**

### 3.2 QuickJS 是什么角色

QuickJS 是 adapter 的**执行运行时**。选它的直接收益是"**一份 adapter，两端运行**"：

- **客户端**：用 QuickJS 执行 adapter，配合传输底座**直连**学校（私密数据不经服务器）。
- **服务端**：Node/TS 服务用 **QuickJS-wasm（`quickjs-emscripten` 一类）**执行**同一份** adapter，用于填充公网的公开数据缓存。两端是同一个 QuickJS 引擎，零语义漂移。（运行时选型见 [`adr_005`](./adr_005_runtime.md)，它覆盖了本文早先"Go + goja"的设想。）

由此，每个学校的对接逻辑只写一次，客户端与服务端共用——这正是"简化上层开发、降低贡献门槛"的落点：贡献者只需写一个 JS 文件，无需懂客户端/服务端/原生。

### 3.3 关键边界：QuickJS 跑逻辑，不碰渲染、不持凭证

- **不碰渲染**：QuickJS 只执行逻辑、不渲染任何 UI，因此不引入 WebView 式卡顿。性能瓶颈在网络 I/O，不在脚本执行；卡顿的真正来源是"在 UI 线程上同步跑重活"，解法是把 adapter 丢到 background isolate，与运行时选型无关。
- **不持凭证**：cookie/token 由可信核心保管，adapter 通过核心暴露的受限方法访问数据（capability-based security / broker 模式）。按信任级别分档（见 §4 与后续 ADR）：
  - **官方签名 adapter** → 能力限定的取数（`core.fetch` 仅在命中 manifest 白名单时注入凭证）；
  - **侧载/第三方 dev adapter** → 退化为 **declarative 纯解析**：核心负责认证+取数，adapter 只把原始响应解析成标准 schema，无网络、无凭证、无副作用。
- **凭证零泄露的更强要求**：不仅"不传凭证的值"，更要"不传任何等价于该凭证的东西"——不给带 token 的完整 URL、交给 adapter 的响应里不残留 `Set-Cookie`、不暴露重定向链中的中间 token。

### 3.4 与传输底座的区分（不要混为一类）

数据 adapter（QuickJS 脚本、I/O 密集、热替换无负担、坏了只影响一个数据源）与**传输底座**（原生模块、长生命周期、有状态、承载全部流量）是**两类东西**，放在同一 capability 体系内管理，但走**两套加载与信任策略**：

| | 数据 adapter | 传输底座（Transport） |
|---|---|---|
| 形态 | QuickJS 脚本 | 原生模块（Go/C + 用户态网络栈） |
| 信任 | 官方签名 / dev 侧载 | **仅官方签名**，release 无侧载入口 |
| 能见度 | 看到单个数据源 | 看到**全部**流量 |
| 故障影响 | 单数据源无数据 | 收敛为"transport 失败 → 降级到只读公开缓存 / 引导系统 VPN" |

## 4. 为什么选这条路（我们在优化什么）

1. **对学校侧变动的韧性**：会变的逻辑下沉为热替换脚本，接口一改推 adapter 即可，不发版。
2. **降低贡献门槛**：贡献者写一个 JS 文件即可，且客户端/服务端共用，社区可参与面最大化。
3. **成本可持续**：公网组件无状态、可静态化，长期开销趋零，不靠捐赠续命。
4. **合规与安全内建**：私密数据客户端直连 / 校内授权处理，公网永不持凭证；最高信任门槛留给能力最大的传输底座。
5. **平台差异隔离**：保留既有 Flutter UI；HarmonyOS 走 OHOS 分支 + FVM 隔离，主线代码不分叉；传输/数据/UI 三层各自可替换。
6. **可演进**：宿主接口契约（capability manifest + 标准 schema）保持稳定，运行时（QuickJS）与传输实现可在不重写宿主集成的前提下替换。

## 5. 舍弃了什么（Consequences / 被拒绝的备选）

任何架构都是取舍，这里明确写下代价，避免日后误以为"免费"。

### 5.1 主动舍弃

- **放弃编译期 per-school 定制**：不为每个学校做编译期微调。代价是某些学校特有的原生能力需用运行时 feature flag 兜，而非编译分叉。收益是单一构建产物，维护面不随学校数膨胀。
- **放弃自建完整 DSL，倾向数据驱动 / SDUI**：不发明一门图灵完备的 UI 语言。代价是 UI 层逻辑表达力受限；收益是不必维护"语言 + 运行时 + 文档"，与"人力不足"的现实对齐。（若日后确需 UI 内逻辑，再单开 ADR 评估。）
- **放弃客户端用 WASM 作插件运行时**：选 QuickJS 而非 WASM。代价是失去多语言与更强沙箱；理由是 I/O 密集负载下二者性能无感差异，而 WASM 在客户端代价大（iOS 禁 JIT 抵消性能优势、需为 OHOS 单独移植、Rust→wasm 工具链抬高贡献门槛）。**保留退路**：capability 契约保持稳定，将来若要做不可信开放插件市场，可换 WASM（客户端 wasm3、服务端用 Node 的 wasm 运行时）而不重写宿主。
- **放弃公网服务端存储私密凭证（默认）**：即便过合规评审，也不默认在公网存 cookie/token。代价是校外私密数据可用性下降（需走校内授权中继或用户侧 VPN）；收益是规避最不对称的安全风险。

### 5.2 接受的代价 / 已知风险

- ~~**服务端选 Go 而非更熟悉的 Node.js**：换取并发、单二进制部署、低运维成本；代价是团队在不熟语言上初期更慢。靠"服务端逻辑保持小而稳"消化这一成本。~~ **（已被 [`adr_005`](./adr_005_runtime.md) 覆盖：服务端改用 Node/TS + QuickJS-wasm。`goja` 的语法缺口与两端语义漂移让 Go 的代价大于收益；本负载是 I/O 密集，Go 的并发优势用不上；单二进制改用 SEA/Docker 补。）**
- **引入第三方 VPN 复刻依赖（如深信服 atrust 的开源复刻）**：作为可替换的传输底座接入。已知风险：协议私有、上游可能停维（但该服务端更新按年、变更频率低，风险被实测频率消解大半）、许可证（GPL3，需谈独立授权或做实进程/模块边界隔离以避免传染）、iOS 上架与后台联网限制。**对策**：当作可热替换的 transport，坏了能换，不焊死；开工前先做"许可证 + 协议模式 + iOS 可行性"三件套探针。
- **微信绑定带来的天花板**：纯小程序绑定（`code2session` + 拿不到 AppSecret）在干净手段下基本无解，唯一可持续解是信息处给正规 API。校外可用性因此进一步依赖校内授权路径。
- **核心成为单点复杂度**：可信核心承载凭证、broker、签名、版本解析等关键职责，必须高质量、不可绕过——它的 bug 影响面最大，需重点测试与审查。
