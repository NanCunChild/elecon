# ADR-007：公网哑服务的部署形态与成本控制

- **状态**：延后（Deferred） 架构约束已由红线 #2（公网零凭证、无状态）+ ADR-000 §2.1 覆盖。部署形态属运维选型，在无实际部署需求时决策缺乏验证手段。
- **日期**：2026-06-14（延后声明）
- **延后理由**：公网哑服务的架构要求已经完全确定（无状态、零凭证、只做分发 adapter + 缓存公开数据）。剩余未定的是**如何部署**——Docker vs Node SEA、CDN 策略、冷启动优化、成本控制——这些是运维/基础设施决策，依赖实际流量模式与预算，当前无足够信息做有意义的选择。

---

## 已确定的架构约束（不需要本 ADR 即已成立）

| 约束 | 来源 |
|---|---|
| 公网服务端不持有任何凭证 | 红线 #2 |
| 无状态——可退化为静态托管 + 极小无状态服务 | ADR-000 §2.1 |
| adapter 执行用 QuickJS-wasm，不用 Node `vm` | ADR-005 |
| 公开数据缓存的时效由 TTL 控制 | ADR-000 §2.4 |
| 不参与 imperative 凭证注入 | ADR-009（第 9 条） |

---

## 原定覆盖内容（留档，待条件成熟时按需展开）

1. **部署形态选型**：Docker 容器 vs Node 单可执行应用（SEA）vs 边缘函数。
2. **adapter 分发方式**：静态文件 CDN vs API 端点 vs Git-based 分发。
3. **缓存策略**：公开数据缓存的存储后端（内存 / Redis / 文件）、TTL 与失效机制。
4. **成本模型**：零捐赠存活条件——最小化长期运营成本的方案。
5. **监控与告警**：无状态服务的健康检查、adapter 执行失败率。

---

## 何时重新评估

- 当公网服务端**实际进入部署阶段**（有真实的 adapter 待分发、有真实的公开数据需缓存）时，再据实际流量预估与预算起草本 ADR。
- 若部署选型**引入架构层面的约束**（如边缘函数平台的执行时间限制影响 adapter 沙箱设计），则需走 ADR。
