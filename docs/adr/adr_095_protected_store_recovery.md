# ADR-095 · 受保护存储不可用时保留数据并重试

- 日期：2026-11-05
- 状态：Accepted（按所有者接续落地授权实施；核心、凭据与原生实现仍需人工实质审阅后合并）。
- 承接：ADR-044、060、061；明确替代 ADR-060 中“硬件解锁失败清除受保护数据”的策略。

## 问题与决定

当前 H 档把硬件检测失败、平台通道异常、解包失败和密文损坏都归为不可恢复，并在启动时删除密钥包与密文。临时不可用不能证明数据永久失效；原生解包也不能为修复不可用状态删除旧密钥并生成替代品。

已有 H 材料存在时，任何无法完成硬件检测、原密钥解包或密文校验的情况都保留原始字节，进入受保护数据不可用状态。界面说明数据尚未清除，提供显式重试；不宣称能自动区分永久损坏和暂时锁定，不循环弹出认证或无限重试。只有重新成功打开原库后才能恢复当前 Profile。原生解包仅查找并使用既有硬件密钥；创建密钥只属于首次保存的新库流程。

仅剩密文而缺少可用密钥材料也不能当作全新 M/S 库。已知 H 失败只重试 H；已选择 S 的损坏密文用原 S key 只读重试，不能重新生成密钥覆盖。探测错误尚不能判断档位时保持阻断，不以降级猜测。界面可显式切换其他已有 Profile；切换等待期间不接纳新恢复，迟到恢复也不得打开已离开的身份。

等待期间不自动降到 S/M，不创建替代密钥，不运行学校脚本、V1 查询或登录，不展示旧业务缓存，也不授予系统 AI 或小部件恢复权限。启动可以完成不含秘密的 Profile/学校元数据读取，但“启动完成”不表示受保护数据已可用。重试成功后重新核验会话代际、已授权来源和当前 Profile，取消旧执行并撤销临时系统 AI 授权；失败或迟到恢复不替换已改变的会话。

本切片只提供无损重试，不新增自动抹除、后台解锁或后台执行入口。永久失效的清除/重建需要后续独立的显式用户操作与持久撤销流程；不能由关闭提示框、普通登录或平台错误隐式触发。

## 消息归档及后续后台边界

按 ADR-061 的既有隔离与事务要求，同一 `CredentialStore` 上的归档合并共享串行队列，在取得运行权后读取最新快照，并在排队前、开始执行及提交时核验同一账号代际；撤销使迟到任务失效，失败不毒化后续队列。这修复核心接口的并发前提，现有前台 Session 队列仍保留。

该队列只协调同一进程内共享的存储对象，不能为两个 Session、FlutterEngine 或进程同时缓存并重写整个 H/S 库提供安全保证。ADR-094 的持久同步仍未启用；实施前必须另行落实唯一存储所有者、跨重启身份撤销和消息/游标/通知候选的持久事务。当前历史分页不能当作新增消息证据。

## 迁移、验证与回滚

不改变 H/S 密文格式、密钥、包 SDK 或领域 schema；旧数据原位重试，不需要重加密。新建 H 库同时写入加密空快照；恢复时若仅有 wrapped DEK 而密文库缺失，无法证明是尚未使用还是文件丢失，保守阻断并保留材料，不把空库称为已恢复。旧 wrapped-only 状态也遵循这一边界。S 档保持原格式的兼容行为：有效 32 字节 `store.dek` 且尚无密文仍视为已同意但未写入条目的空 S 库，不将 H 的新建规则强加给旧 S 数据。回滚到旧版本可能再次走自动清除路径，应保留本恢复策略而非建议用户以降级修复密钥故障。

合成验证覆盖平台暂不可用、异常与坏密文均不修改原始材料，重试后恢复原条目，等待期间拒绝执行和持久降级，并发重试合并、会话变化使迟到恢复失效。同库多归档实例并发不得丢更新，排队中撤销、重登及合并失败后队列可继续。Android 构建与原生既有密钥路径单独核对；测试不代替真实硬件解锁、学校或人工安全验收。
